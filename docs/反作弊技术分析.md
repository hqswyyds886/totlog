# The Outlast Trials 反作弊技术分析

> 全部结论来自本机实测（游戏目录 + 系统注册表 + EOS 日志），不是网上转述。
> 采集时间：2026-10 / 本机 Steam 库。

---

## 一、结论先放

| 问题 | 实测答案 | 证据来源 |
|------|---------|---------|
| 用什么反作弊 | **Easy Anti-Cheat（EOS 版），内核级** | Steam 商店页 + 本机安装 |
| 是不是用户态 | **不是，内核驱动** | `EasyAntiCheat_EOS.sys`，40MB，Type=16 |
| 引擎 | **UE 4.27.1**（Red Barrels 自 fork） | `OPP.log` 的 `Engine Version` |
| 联机是否真启用 | **是，联机时逐局 BeginSession** | 日志里 4 次会话，Mode=1 |
| GitHub 有开源项目吗 | **有，但绝大多数是投毒诱饵** | 见第四节 |

网上和不少"外挂群"的说法是"这游戏是 UE5.5、EAC 是假的/只做启动校验"。**两条都对不上本机实测**：引擎是 4.27.1，EAC 是带 40MB 内核驱动的真家伙，而且每一局联机都在重新协商会话。

## 二、反作弊的实测证据

### 2.1 Steam 商店页的官方声明

```
Uses Kernel Level Anti-Cheat
Easy Anti-Cheat
- Requires manual removal after game uninstall
```

`Uses Kernel Level Anti-Cheat` 是 Valve 强制要求开发者披露的字段，不是玩家猜的。

### 2.2 本机安装形态

游戏目录 `<SteamLib>\steamapps\common\The Outlast Trials`：

```
EasyAntiCheat/EasyAntiCheat_EOS_Setup.exe     959,216   安装器
OPP/Binaries/Win64/TOTClient-Win64-Shipping.exe 119MB   真正的游戏主体
start_protected_game.exe                    3,975,920   EAC 引导壳
TOTClient.exe                                 433,664   启动引导
```

`start_protected_game.exe` 的数字签名：

```
Status : Valid
Signer : CN=EasyAntiCheat Oy, O=EasyAntiCheat Oy, L=Helsinki, C=FI
SERIALNUMBER=2585063-4
```

### 2.3 安装脚本里写死了产品 ID

`installscript.vdf`：

```
"process 1"  "%INSTALLDIR%\EasyAntiCheat\EasyAntiCheat_EOS_Setup.exe"
"command 1"  "install <productid>"
```

`Settings.json`：

```json
{
  "title": "The Outlast Trials",
  "executable": "OPP/Binaries/Win64/TOTClient-Win64-Shipping.exe",
  "productid": "<productid>",
  "sandboxid": "<sandboxid>",
  "deploymentid": "<deploymentid>"
}
```

productid 是 EAC 侧的身份标识，换游戏换 ID，这个值在本地是明文可见的。

### 2.4 驱动确实在系统里

```
服务名   : EasyAntiCheat_EOS
状态     : Stopped / Manual
ImagePath: "C:\Program Files (x86)\EasyAntiCheat_EOS\EasyAntiCheat_EOS.exe"  (Type=16 → 内核驱动)
```

```
C:\Program Files (x86)\EasyAntiCheat_EOS\EasyAntiCheat_EOS.exe       1,041,336
C:\Program Files (x86)\EasyAntiCheat_EOS\EasyAntiCheat_EOS.exe.bak   1,039,800
C:\Program Files (x86)\EasyAntiCheat_EOS\EasyAntiCheat_EOS.sys      40,474,272
```

Type=16 是 `SERVICE_KERNEL_DRIVER`。40MB 的 `.sys` 说明里面不只是个壳——那是带着自研虚拟化/完整性校验模块的量级。

**服务现在是 Stopped，因为它 Manual 启动、只在游戏启动时才拉起来。这不代表"没启用"。**

### 2.5 联机时逐局协商（最硬的证据）

`%LOCALAPPDATA%\OPP\Saved\Logs\OPP.log`，同一次开机内：

```
[2026.10.17-11.20.43:023] LogEOSSDK: LogEOSAntiCheat: [AntiCheatClient] [BeginSession-003] Mode: 1
[2026.10.17-11.20.43:025] LogOnlineRBAntiCheat: OSS: EOS_AntiCheatClient_BeginSession SUCCESS
[2026.10.17-11.21.19:513] LogOnlineRBAntiCheat: OSS: EOS_AntiCheatClient_EndSession SUCCESS

[2026.10.17-11.21.20:017] [BeginSession-003] Mode: 1   → SUCCESS
[2026.10.17-11.22.38:809] EndSession SUCCESS

[2026.10.17-11.22.39:539] [BeginSession-003] Mode: 1   → SUCCESS
[2026.10.17-12.30.08:667] EndSession SUCCESS          ← 这一局 1 小时 07 分
```

用本项目自带的 `totlog` 跑出来：

```
-- EAC 会话 (4 次) --
   #1  19:20:43  36s      Mode=1  建会话=OK  正常关闭
   #2  19:21:20  1m18s    Mode=1  建会话=OK  正常关闭
   #3  19:22:39  1h07m29s Mode=1  建会话=OK  正常关闭
   #4  20:30:10  55s      Mode=0  建会话=OK  正常关闭
   联机总时长: 1h10m18s
```

**关键点：`BeginSession` / `EndSession` 是成对出现的，每进一次联机场景就重新开一次会话。** 那种"只在校验启动、进游戏后就不管了"的说法，在这里直接被日志否定——整个 1 小时 07 分的对局期间会话一直开着。

`Mode: 1` 是 EOS AntiCheat 的客户端模式（Client），服务端侧还有对应的一侧在接受上报。

## 三、它到底在防什么（机制层）

EAC EOS 版的工作方式，和传统"扫内存特征码"不太一样，重点是三件事：

### 3.1 完整性校验（Integrity）

客户端持续对以下对象做校验，结果通过 `AddNotifyClientIntegrityViolated` 这条通道往外报：

- 游戏主模块的代码段（有没有被打补丁）
- 关键导入表项（有没有被 IAT hook）
- 已加载模块列表（有没有多出不该有的 DLL）
- 驱动侧还会看进程的 VAD 树（有没有来路不明的可执行内存映射）

日志里能看到这条通道被显式绑定：

```
[AntiCheatClient] EOS_AntiCheatClient_AddNotifyClientIntegrityViolated bound with NotificationId=[50]
```

### 3.2 上报通道（MessageToServer）

```
[AntiCheatClient] AddNotifyMessageToServer bound with NotificationId=[49]
```

这条是**唯一**把检测结果送出去的管道。客户端本身不封人，它只负责上报；判定在服务端。

### 3.3 会话绑定（Session）

反作弊会话和联机会话是绑在一起的。这就是为什么日志里每局都要 `BeginSession`——服务器不接受一个"没有 EAC 会话"的联机连接。

## 四、GitHub 开源项目实况

用 GitHub 搜索 API 实测（`search/repositories`，关键词 outlast trials / outlasttrials / esp / sdk / mod）：

### 4.1 真有东西的：一个

**[`AIN-sch/outlast-trials-cheat`](https://github.com/AIN-sch/outlast-trials-cheat)** — 创建于 2026-10-11，C++

作者写的是**分析笔记**，不是外挂。README 里明确写了"不是外挂，也不教开挂"。内容含金量高，而且是可验证的实测记录：

- Dumper-7 在这游戏上崩（`Could not find GNames!`），两条特征码都对不上，作者给了手动配 offset 的改法
- **EAC 正常运行时，外部读内存被内核拦死**：`ReadProcessMemory` → err=5，`NtReadVirtualMemory` → `0xC0000022`，**连自己拼 stub 的裸 syscall 也是 `0xC0000022`**，`NtQueryVirtualMemory` 放行，`OpenProcess(ALL_ACCESS)` 提权后成功但读的时候不给
- 结论："拦截在内核里，用户态怎么绕都没用。提权也没用——句柄给你了，读的时候不给。"
- stub 掉 EAC 出口后能读能注，但**联机会被踢**（`Authentication timed out (1/3)`）
- 崩溃上报 `CrashReportClient.exe` 会上传带模块列表的 minidump，得拦

**注意**：这位作者自己也踩了版本坑——他写的引擎是 `UE 5.5`，但本机日志实测是 **4.27.1**。他给的那套 offset（`GNames=0x6EB2C00`、`GObjects=0x6F21838`）是**他那个版本**的 RVA，游戏一更新（本机是 `release-7-1-CL-260801`）全部作废。这正是这类项目的根本问题：**偏移是易腐品**。

### 4.2 其余的基本是投毒/引流

| 仓库 | 判断 |
|------|------|
| `Ondolphige/The-Outlast-Trials-Ultimate-Assistant` | **典型窃密诱饵**。仓库里只有一个 README + 一个 `helper.py`，真正的"外挂"放在**外部网盘的加密压缩包**里（README 直接给出解压密码），并让你"把杀软加例外，这是误报"。文件列表里没有任何可编译源码。链接与密码不在此复述，见调研文档的鉴别章节。 |

## 五、为什么"联机好用 + 不被检测"这两条凑不齐

这是结构性的，不是技术不够。

### 5.1 三条路都堵死

| 路线 | 联机可用 | 检测风险 | 卡在哪 |
|------|---------|---------|--------|
| **外部只读 + 外部绘制** | ❌ | 无（不碰进程） | EAC 内核拦 `ReadProcessMemory`/裸 syscall，`0xC0000022`。不 stub 就什么都读不到 |
| **stub 掉 EAC 出口** | ❌ 被踢 | 高 | 服务器收不到 EAC 会话，`Authentication timed out`，3 次踢出。等于自曝 |
| **注入 DLL + hook** | ⚠️ 可能 | 最高 | 完整性校验直接命中：IAT hook、多出来的模块、VAD 里的可执行页。作者实测"带 hook 的 DLL 一注，游戏直接起不来" |

### 5.2 数值类功能还有第四层墙

作者实测并在本机逻辑上成立：**血量、耐力、位置这些字段服务器说了算**。本地改了，服务器下一帧盖回去。所以"无限耐力""无敌"这类在联机里根本不生效——不是代码写错了，是架构决定的。

### 5.3 所以真正能"联机实用"的只剩两类

1. **信息类，且数据源在本地**（不影响他人、不碰游戏进程）：战绩统计、对局复盘、地图/关卡数据整理 —— 这是本项目在做的
2. **纯本地/单机场景**的玩法调整 —— 但离开联机就谈不上"联机实用"

## 七、UE 对象遍历原理（学术向，不用于联机）

记录在这里是因为它是理解 UE 反作弊设计的关键，也是 `totlog` 未来做地图可视化的理论基础。

UE 世界里所有对象都在两个全局结构里：

```
GNames  (FNamePool)          → 名字池，按 FNameIndex 查字符串
GObjects(TUObjectArray)      → 所有 UObject 指针的稀疏数组
```

遍历流程：

1. 从模块基址 + `GNames` 的 RVA 拿到 FNamePool
2. 池子结构（UE4.27 / UE5 通用）：
   ```
   pool + 0x00  锁
   pool + 0x08  MaxChunkIndex (uint32)
   pool + 0x0C  ByteCursor    (uint32)
   pool + 0x10  Chunks[]      块指针数组（直接就是，不要再解一层）
   ```
3. 块大小 `0x20000`，索引换算 `entry = chunk[idx >> 16] + (idx & 0xFFFF) * 2`
   —— 是**块内字节偏移除以 2**，不是"第几个 entry"。这是最常见的理解错误
4. FNameEntry header 2 字节：`len = header >> 6`，`wide = header & 1`
5. `GObjects` 是 `FChunkedFixedUObjectArray`，item 大小 `0x18`
6. UObject 头：`Class @ 0x10`、`Name @ 0x18`
7. 自检：`chunk[0]` 开头必须是 `None / ByteProperty / IntProperty / BoolProperty`，对不上说明 RVA 错了

**但**：这套东西要在联机用，就必须先过 EAC 那一关；而过了 EAC 那一关，联机就进不去。这就是第五节的死循环。
